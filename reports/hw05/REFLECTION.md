# Reflection

In the selected agent run, the harness received a request to continue and passed it to the model adapter. On the first step, the adapter proposed the `search` tool with a bounded query. The harness did not call a tool directly from model text; it passed the named tool and structured inputs through `execute_tool`, which returned the shared `{ok, data, error}` envelope. The result was appended to the per-step JSONL record with the step number, inputs, tool name, and returned data. The same process repeated on the second step. Because the mock model was intentionally supplied with more calls than the configured two-step budget, the loop stopped at the `max_steps` ceiling. It wrote a final summary event containing the step count, tool-call count, and stop reason. No exception escaped the tool boundary, and no live model, API key, database, or network was needed for this test. A separate safety-rule run sends an aggregate request that asks for restricted unavailable inventory; `execute_tool` returns `ok: false`, the harness records the blocked result, and the agent stops with `safety_rule_block`. This distinction makes the stop cause auditable: the ceiling indicates bounded work, while the safety stop indicates a policy decision.
